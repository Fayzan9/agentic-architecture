# Legal RAG — Assessment of the System Already Being Built

**Context:** this project isn't designing a legal RAG chatbot from a blank page — there is already a real, concrete engineering plan in motion (internally: porting "Sophia" into the PDI platform documented in `../../../usecase/pdi/`) that answers questions over the company's own governing documents, with citations, for both internal staff and external clients. This document evaluates that real, planned system against the risk picture in `01-the-stakes-and-why-naive-rag-fails.md` and the 2026 state of the art — separating what it already gets right from what's genuinely missing.

## What the existing plan already gets right

### A managed, non-naive retrieval backend
Retrieval is not a hand-rolled top-k vector search — it goes through a managed search platform's knowledge-base retrieval capability, which already provides hybrid search and reranking as built-in platform features, plus native multi-turn query understanding (the last several turns of a conversation are passed directly to the retrieval call, and the platform resolves follow-up questions like "what about for part-time employees?" in context, with no custom query-rewriting code needed on this project's side). **This already clears the "naive top-k" bar** described as a baseline failure mode in external research (a benchmark found naive RAG answers only ~44% of factual questions correctly, versus ~63% for advanced RAG techniques) — the underlying platform already provides hybrid retrieval and reranking as first-class features, not something that needs to be built from scratch.

### A deterministic, code-level visibility/citation filter — not a prompt-based one
Before any retrieved content ever reaches the language model, a citation-policy step checks *where* each retrieved chunk actually came from and decides, based on which persona is asking (internal employee vs. external customer), what's allowed to be seen and cited at all. Internal-only content is designed to never reach an external customer's answer — even indirectly. Critically, **this is enforced in code, not by asking the model nicely in a prompt** — which is exactly the right instinct, and directly consistent with this project's own established principle (`../04-agent-harness-and-sandboxing.md` Component 5: guardrails must be enforced independent of the prompt, so a prompt injection or a model's own inconsistency can't talk its way around them).

### Deterministic abstention when there's nothing safe to answer from
If nothing survives the visibility filter, the system is designed to skip the language-model call entirely and return a fixed "I don't have information about that" response — rather than letting the model try to answer anyway with whatever it already knows. This is a real, working instance of exactly the kind of code-level abstention gate that `01-the-stakes-and-why-naive-rag-fails.md` §3 argues is necessary given that even reasoning-tuned models are demonstrably worse at self-recognizing when they don't actually know something.

### A structured, categorized feedback loop already designed in
Feedback isn't just a generic thumbs up/down — it's captured with a specific category, and the category list already includes exactly the failure modes this whole document set is worried about: **"wrong-or-missing-citation," "visibility-rule-broken," "should-not-have-answered,"** and **"should-have-answered-but-abstained."** A flagged answer can already be exported as a permanent test case. This is, in effect, an early version of the "golden-set built from real production failures" practice that `04-evaluation-and-launch-gates.md` describes as best practice — the mechanism for building it already exists in the plan, it just needs to actually be used systematically (see the gaps below).

### An explicit regression test guarding the single most safety-critical behavior
There's already a named "canary test" whose specific job is to verify the internal/external visibility boundary never leaks — and the existing plan itself explicitly calls this out as **"the single most safety-critical piece of behavior in the whole migration."** That's the right judgment call, and it's a real, already-built regression check, not just a stated intention.

## What's genuinely missing, evaluated against the 2026 state of the art and the real-world risk picture

### 1. No verification that a citation's claim is actually supported by the cited text
This is the single most important gap, and it maps directly onto the biggest finding in `01-the-stakes-and-why-naive-rag-fails.md`: the Stanford study found top legal AI vendors hallucinating on 17–33% of queries *despite* those products already using retrieval and displaying citations. **A citation being present, and a citation actually supporting the specific claim attached to it, are two different things** — and the existing plan's citation-policy step only checks *where a chunk came from* (its visibility tier), not *whether the model's generated sentence is actually entailed by that chunk's text*. External research names concrete, adoptable techniques for exactly this: an entailment-verification pass (checking that a generated claim is logically supported by its cited source, not just topically related to it) and a deterministic "clause ID + verbatim quoted span" check performed in code after generation — reject or retry any answer where the cited clause ID doesn't exist in the retrieved set, or where the quoted text doesn't match the source verbatim. **This should be treated as the highest-priority addition to the existing plan**, not a future nice-to-have — see `03-recommended-architecture.md` §2.

### 2. Chunking is not yet clause-aware
A 2026 practitioner guide focused specifically on contract-review RAG states this plainly: *"clause-level retrieval is the right primitive for contract review, not chunk-level... the clause is the unit of legal reasoning. Token-counted chunking cuts across that unit and produces plausible answers that fail in legal review."* The existing plan's chunking configuration lives in a separate provisioning/setup process (outside the running application, per the existing plan's own notes) and isn't described as clause-aware. This is worth a direct, deliberate review — see `03-recommended-architecture.md` §1.

### 3. No explicit handling of document supersession/versioning in retrieval
This is a real, named, actively-researched problem in exactly this domain — a 2026 paper introduces "Controlling Authority Retrieval" as a distinct retrieval objective specifically because standard retrieval "fails structurally" when the correct answer depends on knowing whether a document has been superseded by a later one, using overruled legal precedent as its own primary example. **This project already has the conceptual solution to this exact problem, just not wired into the chat system yet**: the PDI Intelligence Engine's "controlling stack" concept (`../../../usecase/pdi/03-deliverable-1-intelligence-engine.md` §D1-S2) already resolves which document version controls a given provision as of a specific date, for the plan-document-assessment use case. **The chat/RAG system should reuse this same resolved-controlling-document concept as retrieval metadata**, rather than re-deriving version-awareness independently — see `03-recommended-architecture.md` §4 for how.

### 4. No structural/hierarchical retrieval for cross-document, "what do all our X documents say about Y" questions
The current design is chunk-and-persona-scoped; it has no explicit mechanism (a knowledge graph, or a hierarchical summary tree) for questions that require synthesizing across many documents in a category rather than pulling from one or two specific chunks. This may be an acceptable, deliberate scope limitation for a first version (see `05-open-questions-and-decisions-needed.md` — this is exactly the kind of complexity that should be added only once a real need is demonstrated, per this project's own Rule-of-Three discipline in `../guidelines/01-guiding-philosophy.md` §4), but it should be a conscious decision, not an unexamined gap.

### 5. No per-response faithfulness scoring or production drift monitoring yet
The plan has a feedback mechanism (a human flags a bad answer after the fact), but nothing described yet automatically scores every live answer for groundedness against its retrieved context at the time it's generated, the way production best practice for high-stakes RAG recommends. There's also no described mechanism for detecting semantic drift as the underlying document corpus changes over time (new documents added, old ones superseded) in ways that could silently invalidate previously-correct retrieval behavior. See `04-evaluation-and-launch-gates.md`.

### 6. No authentication yet — an explicitly acknowledged, real, current gap
The existing plan is explicit and honest about this: there is no login, no per-user thread ownership, and no access gate on document management or feedback in the current phase — every endpoint is open. This is described as a deliberate, temporary simplification to get the feature working end-to-end first, with real authentication planned as an explicit follow-up phase (and the underlying database schema already has the audit columns reserved for it). **This is not a design flaw in what's been built so far** — it's a clearly-scoped, honestly-labeled deferral — but it must be treated as a hard blocker before any external-persona access goes to real production, since the entire internal/external visibility boundary this system is built around is meaningless without real authentication behind it.

## Summary verdict

The existing plan is a genuinely solid foundation — it already avoids the naive-RAG failure mode, already enforces its most safety-critical rule (visibility) in code rather than in a prompt, and already has the bones of a feedback-driven regression suite. The gaps are specific and addressable, not indicative of a flawed approach: **citation-claim verification (not just source-visibility filtering) is the single highest-priority addition**, followed by clause-level chunking, reusing PDI's existing document-supersession logic in retrieval, and building out the evaluation/monitoring discipline before this reaches external users in production. `03-recommended-architecture.md` and `04-evaluation-and-launch-gates.md` detail exactly how.
